<p><em>This post is written by Michael Haken, Senior Principal Solutions Architect, AWS</em></p> 
<p>Today, we’re announcing support for zonal shift in <a href="https://aws.amazon.com/ec2/autoscaling/" rel="noopener" target="_blank">Amazon EC2 Auto Scaling</a>. Zonal shift allows you to rapidly recover from application impairments in a single <a href="https://aws.amazon.com/about-aws/global-infrastructure/regions_az/" rel="noopener" target="_blank">Availability Zone (AZ)</a> impacting your Auto Scaling Group (ASG) resources. In this post, we describe how performing an ASG zonal shift fits in to a multi-AZ resilience strategy and considerations for how to use the feature with different architectures.</p> 
<h2>Overview</h2> 
<p>Using multiple AZs is an architectural <a href="https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_fault_isolation_multiaz_region_system.html" rel="noopener" target="_blank">best practice</a> for building resilient applications on AWS. Deploying your application across multiple AZs makes your applications more available, fault tolerant, and scalable. EC2 Auto Scaling enables you to further enhance your application’s availability and fault tolerance by dynamically scaling your <a href="https://aws.amazon.com/ec2/" rel="noopener" target="_blank">Amazon Elastic Compute Cloud (Amazon EC2)</a> instances across multiple AZs and replacing them when they’re unhealthy.</p> 
<p>AZs in AWS represent a <a href="https://docs.aws.amazon.com/whitepapers/latest/aws-fault-isolation-boundaries/abstract-and-introduction.html" rel="noopener" target="_blank">fault isolation boundary</a>, meaning that failures from various sources are contained to a single AZ, whether caused by a bad deployment, networking issues, power loss, or operator error. In 2023, we <a href="https://aws.amazon.com/about-aws/whats-new/2023/01/general-availability-amazon-route-53-application-recovery-controller-zonal-shift/" rel="noopener" target="_blank">launched zonal shift</a>, part of <a href="https://aws.amazon.com/application-recovery-controller/" rel="noopener" target="_blank">Amazon Application Recovery Controller (ARC)</a>, which allows you to <a href="https://aws.amazon.com/blogs/networking-and-content-delivery/rapidly-recover-from-application-failures-in-a-single-az/" rel="noopener" target="_blank">Rapidly recover from application impairments in a single AZ</a> by shifting traffic at your <a href="https://aws.amazon.com/elasticloadbalancing/" rel="noopener" target="_blank">Elastic Load Balancing (ELB)</a> load balancer.</p> 
<p>Zonal shift for EC2 Auto Scaling enhances this capability for users who have already implemented recovery patterns for single AZ impairments. It also provides recovery capabilities for architectures that aren’t load balanced by allowing you to prevent new instance launches in a specified AZ. Without zonal shift, when EC2 Auto Scaling detects consistent launch failures in an AZ, the service tries to launch instances in other AZs configured for the ASG. However, certain conditions, like <a href="https://docs.aws.amazon.com/whitepapers/latest/advanced-multi-az-resilience-patterns/gray-failures.html" rel="noopener" target="_blank">gray failures</a>, can cause post-launch problems in a single AZ that EC2 Auto Scaling doesn’t detect. For example, successfully launched instances in a single AZ experience elevated error rates downloading their configuration files over a zonal <a href="https://aws.amazon.com/s3/" rel="noopener" target="_blank">Amazon S3</a>, <a href="https://aws.amazon.com/vpc/" rel="noopener" target="_blank">Amazon Virtual Private Cloud (Amazon VPC)</a> <a href="https://docs.aws.amazon.com/vpc/latest/privatelink/privatelink-access-aws-services.html">interface endpoint</a>. The instances can’t correctly configure their application software and respond to requests with errors. Alternatively, the single-AZ impairment could cause the instance to fail its health checks after provisioning. This causes EC2 Auto Scaling to constantly recycle instances in the impaired AZ, leading to the application running with less capacity than desired.</p> 
<p>Although you might choose to perform a zonal shift at your load balancer to mitigate the impact caused by the event, new instances can still be launched in the impacted AZ and don’t receive incoming requests. Even if your application architecture doesn’t use load balancers, zonal shift for EC2 Auto Scaling can help you recover from single-AZ impairments by allowing you to prevent instance launches in the impaired AZ.</p> 
<h2>Using EC2 Auto Scaling zonal shift to recover</h2> 
<p>To use zonal shift on your ASG, you need to configure it with an <code>AvailabilityZoneImpairmentPolicy</code> parameter either when you create a new ASG or update an existing one. This parameter has two options, <code>ZonalShiftEnabled</code> that enables or disables the ability to perform zonal shifts, and <code>ImpairedZoneHealthCheckBehaviour</code>. The latter option allows you to choose between ignoring or replacing instances identified as unhealthy by EC2 Auto Scaling. First, we look at how you can use zonal shift with a standalone ASG architecture.</p> 
<h3>Standalone ASG zonal shift</h3> 
<p>This architecture uses a standalone ASG without being integrated with an ELB load balancer. Workloads with a standalone ASG commonly perform event driven work such as generating load against a target based on a schedule or processing messages from a queue. The architecture in the following figure uses an ASG that reads messages from an <a href="https://aws.amazon.com/sqs/" rel="noopener" target="_blank">Amazon Simple Queue Service (Amazon SQS)</a> queue, performs some processing on the message data, and writes the results into an <a href="https://aws.amazon.com/rds/aurora/">Amazon Aurora</a> database. The instances communicate with Amazon SQS using a <a href="https://docs.aws.amazon.com/whitepapers/latest/aws-privatelink/what-are-vpc-endpoints.html" rel="noopener" target="_blank">VPC endpoint</a> in each AZ. Each message varies in size, thus the instances use a heartbeat pattern to update the message <a href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html" rel="noopener" target="_blank">visibility timeout</a> until they finish processing it. EC2 Auto Scaling scales instances based on the queue depth, which helps make sure that messages are <a href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/best-practices-processing-messages-timely-manner.html" rel="noopener" target="_blank">processed in a timely manner</a>.</p> 
<p><a href="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-1-EC2-instances-deployed-across-three-AZs-that-process-messages-from-an-SQS-queue.png"><img alt="Figure 1: EC2 instances deployed across three AZs that process messages from an SQS queue" class="size-full wp-image-22986 aligncenter" height="2099" src="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-1-EC2-instances-deployed-across-three-AZs-that-process-messages-from-an-SQS-queue.png" width="2484" /></a></p> 
<p style="text-align: center;"><em>Figure 1: EC2 instances deployed across three AZs that process messages from an SQS queue</em></p> 
<p>Say that a networking degradation causes instances in AZ 1 to experience elevated error rates when attempting to write to the Aurora database, resulting in a 2x increase in the p50 processing latency. The instances in AZ 1 continue to heartbeat until they time out, keeping the message hidden and preventing other healthy instances from taking over the work. As a result, the queue depth grows and EC2 Auto Scaling deploys a new instance, as shown in the following figure.</p> 
<p><a href="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-2-EC2-Auto-Scaling-launches-a-new-instance-in-AZ-1-in-response-to-the-queue-depth-growing.png"><img alt="Figure 2: EC2 Auto Scaling launches a new instance in AZ 1 in response to the queue depth growing" class="size-full wp-image-22985 aligncenter" height="2099" src="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-2-EC2-Auto-Scaling-launches-a-new-instance-in-AZ-1-in-response-to-the-queue-depth-growing.png" width="2484" /></a></p> 
<p style="text-align: center;"><em>Figure 2: EC2 Auto Scaling launches a new instance in AZ 1 in response to the queue depth growing</em></p> 
<p>The new instance lands in AZ 1 and experiences the same problem as the other instance, thus it can’t decrease the queue depth and processing latency. Instead, it exacerbates the issue by consuming additional messages that aren’t successfully processed. The instances in AZ 1 never appeared unhealthy, thus EC2 Auto Scaling didn’t take any actions to replace them. To mitigate this problem, you can start a zonal shift for your ASG. This makes sure that any future instance launches only happen in AZ 2 or AZ 3, as shown in the following figure.</p> 
<p><a href="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-3-After-the-zonal-shift-new-instances-are-only-launched-in-AZ-2-and-AZ-3-by-EC2-Auto-Scaling.png"><img alt="Figure 3: After the zonal shift new instances are only launched in AZ 2 and AZ 3 by EC2 Auto Scaling" class="size-full wp-image-22983 aligncenter" height="1096" src="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-3-After-the-zonal-shift-new-instances-are-only-launched-in-AZ-2-and-AZ-3-by-EC2-Auto-Scaling.png" width="992" /></a></p> 
<p style="text-align: center;"><em>Figure 3: After the zonal shift new instances are only launched in AZ 2 and AZ 3 by EC2 Auto Scaling</em></p> 
<p>You have the option to mark the instances as unhealthy using the <a href="https://docs.aws.amazon.com/autoscaling/ec2/APIReference/API_SetInstanceHealth.html" rel="noopener" target="_blank">SetInstanceHealth API</a> to force EC2 Auto Scaling to replace these instances to prevent them from continuing to contribute to additional latency and errors. Changing the instance health state is considered a mutating change and relies on the EC2 Auto Scaling <a href="https://docs.aws.amazon.com/whitepapers/latest/aws-fault-isolation-boundaries/control-planes-and-data-planes.html" rel="noopener" target="_blank">control plane</a>. Therefore, you should avoid making this a critical step in your recovery plan. When you are confident that the impairment has abated, you can cancel the zonal shift, which causes EC2 Auto Scaling to automatically rebalance capacity across your AZs.</p> 
<h2>ASG with ELB zonal shift</h2> 
<p>In this section we observe how to use zonal shift with an ASG that is serving traffic from an ELB. We also examine how the <code>ImpairedZoneHealthCheckBehavior</code> affects recovery in this situation. In this architecture, the instances in the ASG read data from the database when they receive HTTP requests from the ELB, as shown in the following figure.</p> 
<p><a href="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-4-A-three-tier-application-deployed-in-three-AZs-using-an-ALB-ASG-and-Aurora-database.png"><img alt="Figure 4: A three-tier application deployed in three AZs using an ALB, ASG, and Aurora database" class="size-full wp-image-22982 aligncenter" height="1998" src="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-4-A-three-tier-application-deployed-in-three-AZs-using-an-ALB-ASG-and-Aurora-database.png" width="2484" /></a></p> 
<p style="text-align: center;"><em>Figure 4: A three-tier application deployed in three AZs using an ALB, ASG, and Aurora database</em></p> 
<p>In this scenario, the instances in AZ 1 start experiencing increased latency with their EBS volumes causing them to respond to requests with errors and fail their <a href="https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/monitoring-system-instance-status-check.html" rel="noopener" target="_blank">EC2 instance status checks</a>. Initially, to mitigate the impact, you can <a href="https://docs.aws.amazon.com/r53recovery/latest/dg/arc-zonal-shift.start-cancel.html#arc-zonal-shift.start" rel="noopener" target="_blank">start a zonal shift</a> at your load balancer to prevent your users from receiving errors. Then, you can initiate a zonal shift for your ASG to prevent new capacity from being launched into the AZ that isn’t receiving traffic.</p> 
<p>If the ASG’s <code>ImpairedZoneHealthCheckBehavior</code> is set to <code>IgnoreUnhealthy</code>, then the instances in AZ 1 that are failing their health checks aren’t terminated by EC2 Auto Scaling, as shown in the following figure. This can be helpful if you’re pre-scaled to handle the loss of an AZ’s worth of capacity by not causing EC2 Auto Scaling to attempt to launch additional instances. It can also make recovery safer by leaving capacity in the AZ, thus when you end your load balancer zonal shift after the impairment ends, the AZ can immediately start receiving traffic again.</p> 
<p><a href="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-5-Performing-a-zonal-shift-on-the-ALB-and-ASG-choosing-to-ignore-unhealthy-instances-in-the-ASG.png"><img alt="Figure 5: Performing a zonal shift on the ALB and ASG, choosing to ignore unhealthy instances in the ASG" class="size-full wp-image-22981 aligncenter" height="973" src="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-5-Performing-a-zonal-shift-on-the-ALB-and-ASG-choosing-to-ignore-unhealthy-instances-in-the-ASG.png" width="908" /></a></p> 
<p style="text-align: center;"><em>Figure 5: Performing a zonal shift on the ALB and ASG, choosing to ignore unhealthy instances in the ASG</em></p> 
<p>Alternatively, you can set the option to <code>ReplaceUnhealthy</code>. Now, instances that are found to be unhealthy by EC2 Auto Scaling are replaced. This option can be helpful if you aren’t pre-scaled to handle the loss of capacity. EC2 Auto Scaling launches new instances into the remaining AZs to bring the ASG back to its desired capacity, as shown in the following figure. However, this approach also has a tradeoff: launching new instances isn’t guaranteed to be successful, thus you might experience delays in acquiring new capacity.</p> 
<p><a href="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-6-Performing-a-zonal-shift-on-the-ALB-and-ASG-this-time-replacing-unhealthy-instances-in-the-remaining-AZs.png"><img alt="Figure 6: Performing a zonal shift on the ALB and ASG, this time replacing unhealthy instances in the remaining AZs" class="size-full wp-image-22980 aligncenter" height="973" src="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-6-Performing-a-zonal-shift-on-the-ALB-and-ASG-this-time-replacing-unhealthy-instances-in-the-remaining-AZs.png" width="908" /></a></p> 
<p style="text-align: center;"><em>Figure 6: Performing a zonal shift on the ALB and ASG, this time replacing unhealthy instances in the remaining AZs</em></p> 
<p>In both situations you must consider whether you have <a href="https://docs.aws.amazon.com/elasticloadbalancing/latest/userguide/how-elastic-load-balancing-works.html#cross-zone-load-balancing" rel="noopener" target="_blank">cross-zone load balancing</a> enabled or disabled. When cross-zone load balancing is enabled, each instance, regardless of its AZ, receives an approximately equal share of the traffic. This means that you can end your zonal shift for both your load balancer and ASG at the same time safely. As EC2 Auto Scaling rebalances your instances across each enabled AZ, they receive the same percentage of traffic.</p> 
<p>If cross-zone load balancing is disabled, then each AZ receives an equal percentage of the traffic, regardless of how many instances are in the AZ. If you’ve chosen to replace unhealthy instances, or if your ASG has scaled during the event, then the capacity across your AZs could have become imbalanced. When you end your load balancer zonal shift and EC2 Auto Scaling begins to rebalance your capacity, you could end up in a situation shown in the following figure, where a single or small number of instances gets an overwhelming portion of the load.</p> 
<p><a href="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-7-A-three-tier-architecture-with-an-imbalance-of-capacity-among-its-three-AZs.png"><img alt="Figure 7: A three-tier architecture with an imbalance of capacity among its three AZs" class="size-full wp-image-22979 aligncenter" height="1998" src="https://d2908q01vomqb2.cloudfront.net/1b6453892473a467d07372d45eb05abc2031647a/2024/11/12/Figure-7-A-three-tier-architecture-with-an-imbalance-of-capacity-among-its-three-AZs.png" width="2484" /></a></p> 
<p style="text-align: center;"><em>Figure 7: A three-tier architecture with an imbalance of capacity among its three AZs</em></p> 
<p>This imbalance can present an overload risk, thus you must specify the <code>--skip-zonal-shift-validation</code> parameter when you enable zonal shift to acknowledge that you understand the risk. However, you can help prevent overload from occurring due to imbalance by using the load balancer’s <code>target_group_health.dns_failover.minimum_healthy_targets.count</code> option and specifying the number of instances that should be present in the AZ. If you’re using three AZs and your desired capacity is 12, then you should set the value to four (which represents one third of the ASGs total capacity). This prevents traffic from being routed to the AZ until there is enough healthy capacity there to handle the load. You may need to dynamically adjust this number as the ASG scales over time. The minimum count you set in the past may not be the right minimum count today.</p> 
<h2>Zonal shift best practices</h2> 
<p>As a set of best practices, we recommend that you:</p> 
<ol> 
 <li>Are pre-scaled to handle the loss of an AZ’s worth of capacity</li> 
 <li>Configure your impairment policy to ignore unhealthy hosts</li> 
 <li>Enable cross-zone load balancing</li> 
</ol> 
<p>With this configuration, you can also safely use <a href="https://docs.aws.amazon.com/r53recovery/latest/dg/arc-zonal-autoshift.html" rel="noopener" target="_blank">zonal autoshift</a>. When zonal autoshift is enabled, AWS automatically starts and ends the zonal shift on your behalf whenever the AWS telemetry indicates there is an impairment affecting a single AZ. This can be used in conjunction with zonal autoshift for your ELB load balancer. If you are not using zonal autoshift, then you can still use the <a href="https://docs.aws.amazon.com/r53recovery/latest/dg/eventbridge-zonal-autoshift.html" rel="noopener" target="_blank">EventBridge observer notifications</a> to inform your zonal shift decisions or start automated processes. Refer to the <a href="https://docs.aws.amazon.com/autoscaling/ec2/userguide/ec2-auto-scaling-zonal-shift.html" rel="noopener" target="_blank">EC2 Auto Scaling zonal shift documentation</a> for more details on the full set of best practices when using zonal shift.</p> 
<h2>Conclusion</h2> 
<p>In this post we showed you the benefits of using zonal shift with your Amazon EC2 Auto Scaling Groups as part of enhancing your resilience in multi-AZ architectures. We explored several scenarios where zonal shift can be used, and reviewed best practices for using zonal shift safely and effectively. To get started using zonal shift with your ASGs, refer to the <a href="https://docs.aws.amazon.com/autoscaling/ec2/userguide/ec2-auto-scaling-zonal-shift.html" rel="noopener" target="_blank">documentation</a>.</p>
